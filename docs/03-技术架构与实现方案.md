# 03 技术架构与实现方案

> 读者：技术负责人与全体工程师。对应 [PRD](02-产品需求文档PRD.md) 的功能编号（A1、E5 等）在本文中直接引用。

---

## 1. 总体架构：境内控制面 + 海外执行面（双平面）

**为什么必须双平面**：
1. 数据源（Google Maps、LinkedIn 公开页、海外官网）与收件方（Gmail/Outlook）在境内无法直连或直连质量差；海外 IP 发信送达率显著更高；
2. 合规：《促进和规范数据跨境流动规定》(2024) 明文豁免——"在境外收集的个人信息传输至境内处理后再向境外提供，且未引入境内个人信息或重要数据的，免予出境安全评估/标准合同/认证"。**前提是严格数据分域**：海外买家线索库绝不混入境内个人信息（如客户企业员工数据）。

```
┌─────────────────────── 境内控制面（阿里云/腾讯云） ───────────────────────┐
│  Web 工作台(Next.js)   主 API(FastAPI)   CRM/线索库(PostgreSQL)          │
│  账务/计费   人审工作台(HITL)   看板   运营后台   国产 LLM(DeepSeek/Qwen)  │
└──────────────────────────────┬───────────────────────────────────────┘
                     内部专线/加密通道（任务指令下行，线索/事件上行）
┌──────────────────────────────┴───────────────────────────────────────┐
│                    海外执行面（AWS/阿里云海外区）                        │
│  采集集群(Playwright/代理池)   Enrichment 瀑布管线   邮箱验证            │
│  发送引擎(SES+域名池+邮箱池)   预热网络   探针服务(打开/点击/CTA落地页)   │
│  IMAP 收件聚合   Webhook 回调(SNS bounce/complaint)   海外 LLM 旁路(可选)│
└───────────────────────────────────────────────────────────────────────┘
```

每条跨境数据链路在设计文档中标注合规依据；架构冻结前就豁免适用性取得律所书面意见（见 04 文档合规岗职责）。

## 2. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Next.js + TypeScript + Ant Design Pro + TanStack Query | 团队易招人、组件生态适配中后台+官网 SEO |
| 主 API | Python FastAPI + Pydantic | 与 AI/数据生态同栈，减少跨语言成本 |
| 数据库 | PostgreSQL（主库+pgvector）| 事务+JSONB+向量一库搞定 MVP；线索全文检索用 pg 内置，量大后再上 OpenSearch |
| 缓存/队列 | Redis + Redis Streams（MVP）→ Kafka（规模化） | 先简后繁 |
| 长时工作流 | **Temporal** | 序列"发送→等 3 天→跟进"跨天状态、重试、幂等、崩溃恢复是原生能力；这是本产品最核心的工程决策 |
| Agent 编排 | LangGraph（或自研轻量状态图） | 管每个节点内部"研究→起草→自检"的多步 LLM 推理；与 Temporal 分层解耦 |
| 采集 | Playwright + Scrapy + 商业代理池；优先商业 API（Outscraper/Apify） | "买 API 别硬爬"原则 |
| 发送 | Amazon SES（多区域）+ 自建域名/邮箱池管理 | $0.10/千封成本最低、最可控；事务邮件与冷触达彻底隔离（不同服务不同域名） |
| LLM | 模型路由层：DeepSeek-V3/Qwen-Max 主力（写信/背调），Qwen 小杯/GLM 跑分类抽取，Qwen 专线小语种；预留海外模型旁路（需海外主体） | 只接已备案模型锁定"登记"轻合规路径；任何单一供应商断供不停摆 |
| 部署 | K8s（或 MVP 期 docker compose + 云托管）+ Terraform | 双平面各一套，IaC 管理 |
| 可观测 | OpenTelemetry + Grafana/Loki + Sentry | 发送链路全程 trace |

## 3. 核心数据模型

```
Company(id, name, domain, country, industry, size, source[], dedup_fingerprint, ...)
Contact(id, company_id, name, title, email, email_status{valid|catchall|invalid},
        email_type{corporate|personal}, linkedin_url, phone, provenance[])   -- 来源留痕 C9
Signal(id, company_id, type{customs_record|hiring|news|website_update}, payload, observed_at)
Lead(id, company_id, owner_id, stage, score, score_reasons[], campaign_id)
Campaign(id, icp_config, sequence_def, sender_pool_id, status, metrics)
SequenceRun(id, lead_id, campaign_id, state, next_action_at, step_index)     -- Temporal workflow 映射
Message(id, lead_id, direction, channel, subject, body, evidence[], approved_by, sent_at,
        opens[], clicks[], reply_intent)
SuppressionEntry(email, reason{unsub|complaint|hard_bounce|invalid}, global=true)
SenderDomain(domain, dns_status{spf,dkim,dmarc}, reputation), SenderMailbox(email, warmup_stage, daily_cap, sent_today)
KnowledgeDoc(tenant_id, type{company|product|case|objection}, content, embedding)
```

关键约束：
- `Contact.email_type=personal` 的记录在发送层被硬性拒绝（PRD C3）；
- 所有出站发送前查 `SuppressionEntry`（全局，不分租户可见但按哈希匹配）；
- `Message.evidence` 存 AI 写信引用的字段快照（可解释性，PRD D1/G4）。

## 4. 六大子系统实现要点

### 4.1 数据采集与瀑布富化（services/enrich）

- **源适配器框架**：每个数据源实现统一接口 `search(icp) -> CompanyCandidate[]`，MVP 接三个：
  - 搜索引擎源（B1）：SERP API（Serper/SerpAPI）+ 官网抓取解析（公司名、简介、联系页邮箱）；
  - 海关源（B2）：ImportGenius/腾道商业 API，按 HS 码返回进口商及交易记录 → 写入 `Signal(customs_record)`；
  - 地图源（B3）：Outscraper/Apify Google Maps 按品类+地区批量采集；
- **瀑布富化管线**（C1）：官网抓取邮箱 → Hunter（域名模式强）→ Snov（性价比）→ 模式猜测兜底；命中即停，成本记账到租户积分；
- **验证管线**（C2）：自建语法+MX 预筛 → ZeroBounce/NeverBounce 终验 → 状态回写；catch-all 标记降权；
- **去重**（B10）：`dedup_fingerprint = f(规范化域名, 规范化公司名, 国家)`，跨源合并策略"字段级最新且来源可信度加权"；
- **爬虫红线**（写进代码评审 checklist）：遵守 robots、限频、只抓公开页面、不碰登录态数据、不抓国内 B2B 平台、UA 表明身份。

### 4.2 AI 研究与写信（services/agent）

三 agent 分工，中间产物结构化、可缓存、可人审：

1. **Research Agent**（C7）：输入公司域名 → 抓 About/Products/招聘/新闻 → LLM 摘要成固定 schema 的"素材卡"：`{做什么, 卖给谁, 规模信号, 近期事件[], 可引用信号[], 切入建议}`；公司级缓存 30–90 天；
2. **Writing Agent**（D1/D3）：字段约束式 prompt——只允许引用素材卡中的已验证字段，输出 `{subject, body, personalization_evidence}`；先生成个性化首句+模板拼接（成本可控），整封生成为高级选项；序列 4 步一次生成；发送前过垃圾词检测（D6）；
3. **Reply Agent**（G2/G3）：规则前置（退订词/NDR/OOO 头零成本拦截）→ LLM few-shot 分类 `{label, confidence, extracted_info}` → 低置信度进人审队列 → 动作路由（感兴趣→RAG 检索企业知识库草拟回复待审；OOO→提取日期顺延 Temporal timer；退订→写 Suppression；转介绍→新联系人回流富化队列）。

**模型路由**：`route(task_type, language, tenant_tier)` → 具体模型；写信主力 DeepSeek-V3/Qwen-Max，分类用小杯，小语种走 Qwen+术语表+回译自检；所有调用带租户级用量计量（积分扣费）与全链路日志（prompt/输出留存，用于评估与申诉）。

**评估体系**：分类准确率基准集（人工标注 500 条起步，每月增量）；写信质量用"人审批准率"做在线指标（PRD 目标 ≥70%）。

### 4.3 发送引擎与送达率基建（services/sender）——最深护城河

- **域名/邮箱池**（E1）：为租户开通/托管专用发信域名（引导购买近似域名），每域 2–3 邮箱，每邮箱日发上限 30–50 封；容量公式产品化："要日发 X 封需 ceil(X/40) 个邮箱、ceil(X/120) 个域名"；
- **DNS 向导**（E2）：自动生成 SPF/DKIM/DMARC/一键退订记录，轮询校验，DMARC 从 p=none 起步收集报告；三件套未通过的域名发送功能锁死；
- **预热**（E3）：自建预热池（租户邮箱互发+系统种子邮箱）或首期集成第三方 warmup 服务；预热阶段状态机 `W1(5-10/天)→W2(15-20)→W3(30-40)→ACTIVE`，发送调度器读取该上限；
- **调度器**（E4）：全局令牌桶（域/邮箱/租户三级）、随机抖动、收件人时区窗口（当地 8:00–17:00）、回复即停（Reply Agent 事件驱动）；
- **序列引擎**（E5）：每个 `SequenceRun` = 一个 Temporal workflow：`send(step) → await timer(3d/7d/7d) or signal(replied/bounced/unsub) → next`；幂等键防重发；
- **抑制与回收**（E6/E7）：SES 的 bounce/complaint SNS → 实时写 Suppression + 指标累计；租户级投诉率 >0.1% 告警、>0.3% 熔断暂停；
- **探针**（E8）：自域名追踪像素+重写链接（注意与三件套域对齐避免伤送达）；CTA 按钮与产品目录落地页部署在海外执行面，行为事件回流 `Signal`；
- **统一收件箱**（E9）：发信邮箱的 IMAP/API 收件轮询聚合 → 归并到 Lead 时间线 → 触发 Reply Agent。

### 4.4 工作台与 CRM（apps/web + services/api）

- 找客户工作流：ICP 表单（A3/A4 AI 辅助生成）→ 源选择 → 结果表格（评分排序、勾选入库）→ 一键建 campaign；
- 人审工作台（G4）：待审队列（模板审批/草稿审阅/低置信度回复），草稿旁展示 `personalization_evidence` 与素材卡引用（"show the why alongside the what"），批量通过/驳回，批准率仪表；
- CRM（H1–H5）：公司-联系人-线索三实体，阶段看板拖拽，时间线聚合 Message/Signal/备注；CSV 导入走同一套验证管线；
- 看板（I1–I4）：以回复率/正向回复率为核心，开信率标注"参考值（隐私保护致虚高）"。

### 4.5 计费与积分（J1）

- 订阅（套餐/席位）+ 计量积分（enrichment 命中、验证、AI 调用）双轨；积分不过期；
- 上游成本记账：每次外部 API 调用记录供应商成本，支撑毛利报表（目标 65–85%）与"数据源质量报表"（I4）。

### 4.6 运营后台与风控（J6）

- 租户健康总览（送达指标、投诉率、用量）；
- 滥用防控：出站内容抽样审核、收件人列表异常（购买名单特征：验证不通过率畸高）、投诉率异常账户限制——平台信誉是所有租户的公共品，必须中心化守护。

## 5. 合规工程清单（代码级落地）

| # | 要求 | 实现 |
|---|---|---|
| 1 | 只触达企业邮箱 | 免费邮箱域名表（gmail/163/hotmail…）+ 发送层硬拒绝 |
| 2 | 一键退订 | List-Unsubscribe + One-Click（RFC 8058）头强制注入；退订 API 即时写全局 Suppression |
| 3 | CAN-SPAM 要素 | 模板渲染强制包含发件方真实身份与实体地址占位符，缺失不允许发送 |
| 4 | GDPR/正当利益 | 欧盟收件人 campaign 创建时强制走 LIA 评估模板（产品内表单留档）；删除/反对请求 API |
| 5 | 数据留痕 | Contact.provenance 记录来源/时间/依据；数据删除级联 |
| 6 | 数据分域 | 海外线索库（执行面）与境内客户数据（控制面）物理分库；ETL 白名单字段清单评审 |
| 7 | 生成式 AI 登记 | 只接已备案模型；登记材料由后端提供技术说明；AI 生成内容标识（对外发布的社媒内容，P2 阶段） |
| 8 | 爬虫红线 | 采集框架内置 robots 解析与限频；代码评审 checklist；禁止反爬突破类代码入库 |

## 6. 单位经济学（容量与成本规划输入）

标准客户（3 域名 × 3 邮箱，日发 ~360 封，月产 ~500 条验证线索）月变动成本估算：

| 项 | 成本 |
|---|---|
| 发信邮箱 9 个 + 域名摊销 | ~$25–35 |
| Enrichment（瀑布命中 500 条） | ~$15–35 |
| 邮箱验证 | ~$8/千次 |
| LLM（国产模型写信+分类） | <¥30（单封 <¥0.05） |
| SES 发送（~8 千封/月） | ~$1 |
| **合计** | **≈ ¥350–800/月** → 标准版 ¥12,800/年毛利 ~65%，专业版 ~80%+ |

## 7. 环境与工程规范

- 环境：dev（单平面模拟）→ staging（双平面缩配）→ prod；发送相关全部变更需在 staging 用内部测试域实测；
- CI：lint + 单测 + 合规 checklist（爬虫/发送代码路径强制 reviewer）；发送引擎与抑制列表要求单测覆盖率 ≥80%；
- 秘钥：云 KMS，邮箱凭证信封加密；
- 灾备：Suppression 列表与信誉数据每日快照——这是全系统最不可丢的数据。

## 8. 技术风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 送达率崩坏（新域被标垃圾） | 高 | 预热纪律产品化强制执行；多域隔离爆炸半径；健康度熔断 |
| 上游数据 API 涨价/断供 | 中 | 瀑布多供应商冗余；源适配器框架让替换成本 O(1) |
| LLM 断供/质量波动 | 中 | 模型路由多活；关键 prompt 带评估基准回归 |
| 采集被目标站封锁 | 中 | 商业 API 优先；代理池与限频；单源失效不影响瀑布整体 |
| 合规变化（AI 备案/数据出境） | 中 | 只接已备案模型；架构冻结前律所书面意见；合规 owner 年度复核 |
| Temporal/双平面复杂度拖慢 MVP | 中 | MVP 期允许"单海外平面+境内只读控制台"的简化拓扑，商业化前完成分域改造 |
