# 05 架构与开发规范（工程师必读）

本文是代码库的「宪法」。所有人（含未来的你）新增/修改代码都遵守它，
这样系统改起来不会到处冒 bug。核心思想一句话：**依赖只能从外向内指，
业务规则不碰 IO，外部依赖藏在接口后面。**

---

## 1. 分层与依赖规则

```
        ┌─────────────────────────────────────────────┐
        │  api/            HTTP 路由装配（最薄）         │
        ├─────────────────────────────────────────────┤
        │  modules/<x>/    业务模块（编排）              │
        │    router → service → repository → models     │
        ├───────────────┬─────────────────────────────┤
        │  ports/       │  domain/                      │
        │  外部依赖接口  │  纯业务规则+枚举+契约（无 IO） │
        ├───────────────┴─────────────────────────────┤
        │  adapters/      端口的实现（fake / real）      │
        ├─────────────────────────────────────────────┤
        │  core/          配置/DB/日志/错误/DI 容器      │
        └─────────────────────────────────────────────┘
```

**铁律（依赖方向）**
1. `domain/` 不 import 任何其它层（不碰 SQLAlchemy、httpx、FastAPI）。它是纯的。
2. `modules/` 只依赖 `domain/`、`ports/`、`core/`。**模块之间不互相 import 对方的 ORM 模型**；
   要用别的模块的能力，通过其 service 或领域契约（`domain/contracts.py`）。
3. 业务代码**永远不 import `adapters/` 里的具体类**，只通过 `core/deps.py` 拿端口实现。
4. `adapters/` 实现 `ports/` 的接口，可依赖 `domain/`、`core/`。
5. 换数据库/供应商/大模型 = 加一个 adapter + 改 `deps.py` 一行，**业务与领域零改动**。

> 为什么这样能防 bug：改动被关在边界内。改发送逻辑不会碰到找客户；换 Hunter 为别家
> 只动一个 adapter；写单测不需要真数据库/真 API。

---

## 2. 模块解剖（每个 modules/<x>/ 的标准结构）

| 文件 | 职责 | 依赖 |
|---|---|---|
| `models.py` | ORM 模型（持久化），继承 `core.database.Base` | SQLAlchemy |
| `schemas.py` | API 出入参（pydantic） | pydantic、domain |
| `repository.py` | 所有 SQL 都关在这里，对外给方法 | models、session |
| `service.py` | 业务编排：调 repository + ports + domain 规则 | repository、ports、domain |
| `router.py` | HTTP 端点，薄；装配 service（走 deps）、校验、调用、返回 schema | service、schemas |

**约束**
- SQL 只出现在 `repository.py`；`service.py` 不写裸 SQL。
- 业务判断尽量下沉到 `domain/rules.py` 的纯函数（可单测），`service.py` 只做编排。
- `router.py` 不写业务逻辑，只做「收参 → 调 service → 返 schema/抛领域异常」。
- 新模块建好后：① 在 `models_registry.py` 登记其 models；② 在 `api/routes.py` 挂载其 router。

## 3. 端口与适配器（外部世界的接线）

**已定义端口**（`ports/`）：`LLMPort`、`DataSourcePort`、`EnrichmentPort`、
`EmailVerifierPort`、`EmailSenderPort`、`ClockPort`。

**加一个新数据源**（例：接入真实海关 API）：
1. 在 `adapters/real/` 写一个类，实现 `DataSourcePort`（`source_type` 属性 + `async search()`）。
2. 在 `adapters/real/data_sources.py` 的 `build_real_data_sources()` 里登记它。
3. 完成。业务层 `LeadService` 一个字都不用改 —— 它只认端口。

**本地 vs 云端**：由环境变量 `ADAPTER_MODE` 控制（见 `core/deps.py`）：
- `local`：`adapters/fake/*`，确定性、零外部调用、零费用 → Mac mini / CI 直接跑。
- `cloud`：`adapters/real/*`，真实 SES / 海关 / 大模型。

写业务与测试时**默认 local**，永远不必碰真实密钥。

---

## 4. 契约（模块间的通用语言）

跨模块传数据用 `domain/contracts.py` 里的 pydantic DTO（如 `CompanyCandidate`、
`GeneratedEmail`、`ReplyClassification`），**不要传对方的 ORM 对象**。端口的入参/出参也用它们。
新增跨模块数据结构 → 加到 `contracts.py`。

---

## 5. 错误处理

- 业务失败抛 `core/errors.py` 里的领域异常（`NotFoundError`/`ValidationError`/
  `ComplianceError`/`ConflictError`/`ExternalServiceError`），不要返回 `(ok, err)` 元组。
- API 层已统一把领域异常转成规范 JSON：`{"error": {"code", "message"}}`。
- **合规拦截一律抛 `ComplianceError`（403）**，调用方不得 try/except 吞掉后继续发送。

---

## 6. 数据库约定

- 模型继承 `Base`（自带 `id`(uuid str)/`created_at`/`updated_at`）。
- 为跨库可移植（SQLite 本地 / Postgres 云端），**列类型只用通用类型**：`String`、`Text`、
  `Integer`、`Float`、`Boolean`、`JSON`、`DateTime(timezone=True)`。
  暂不用 Postgres 专有的 `JSONB`/`ARRAY`/`pgvector`（上云后按需替换，不影响业务）。
- 异步 SQLAlchemy 注意：**别对已持久化对象的关系集合做惰性访问**（会 MissingGreenlet）。
  构建对象图时先 append/赋值好关系集合再 flush；查询用 `lazy="selectin"` 或显式 `selectinload`。
- 本地/MVP 用 `Base.metadata.create_all`（`init_db`）；生产改 Alembic 迁移。

---

## 7. 测试约定

- 框架 pytest + pytest-asyncio（`asyncio_mode=auto`，async 测试直接 `async def`）。
- 用 `conftest.py` 的 `session` 夹具（内存 SQLite，每测独立、快）。
- 优先测 `domain/` 纯函数（最高性价比）与 service 编排（用 fake 适配器，确定性）。
- 关键红线必须有测试：合规拦截、去重幂等、送达频控、抑制列表。
- 提交前：`make test` 绿、`make lint` 绿。

### orchestration 编排层（唯一允许组合多个业务模块的地方）

业务模块之间互不依赖（低耦合），但完整获客闭环需要把它们串起来。这件事集中在
`modules/orchestration/`：它只做「编排」不含业务规则，通过调用各模块的 service 组合出
麦穗「五步法」在我们架构下的自动化流水线：

```
campaign 目标(campaigns) → AI 研究+写信(agent) → 人审 HITL(agent)
   → 批准后入发送序列(sending) → 预热/序列推进(sending)
   → 入站回复分诊(agent) → 停序列/抑制/CRM 阶段跃迁(sending+compliance+crm)
```

关键端点：`/orchestration/campaigns/{id}/prepare`（AI 逐目标备信进人审队列）、
`/launch`（只把已批准草稿入队 —— HITL 铁律：首封信必须人审）、`/quick-launch`（模板直发）、
`/inbound`（回复分诊）、`/tick`（系统心跳：预热+序列步进，生产由定时器每分钟调）。
